# KeyMouse 项目目标与交付边界

## 项目定位

KeyMouse 是一个可被其他程序嵌入的底层输入库，不是桌面应用、配置工具或自动化产品。

它的职责是向 TypeScript/Node.js 和 Python 开发者提供统一的系统级键盘、鼠标事件监听、选择性拦截和快捷键触发能力，同时把 Windows、macOS、Linux X11 和 Linux Wayland 的差异封装在原生后端中。

## 一句话目标

到 v1.0，KeyMouse 应成为一个可安装、可验证、可长期维护的开源 C++ 输入库：同一套原生内核和语义契约服务于 TypeScript/Node.js 与 Python，并按平台能力矩阵提供真实的全局监听、快捷键注册和选择性拦截。

## 仓库交付什么

### 1. C++ 输入内核

- 统一键盘、鼠标、设备、时间戳和输入帧事件模型。
- 修饰键、按下/松开配对、组合前缀、chord、长按和重复触发状态机。
- 不可变规则快照、冲突处理和同步 `Pass` / `Consume` 决策。
- 启停、Hook/Event Tap 失效、休眠、锁屏、热插拔和权限恢复。
- 结构化能力、错误、背压和运行状态。
- 面向语言绑定的有界异步通知。

拦截决策必须在原生层同步完成，不等待 Node.js 事件循环、Python GIL 或 IPC 回调。

### 2. 平台后端

- Windows 低级键盘/鼠标监听与选择性拦截。
- macOS CGEventTap 及必要的设备级路径。
- Linux X11 的监听、快捷键注册和可实现的拦截路径。
- Linux Wayland 的 Portal 能力与 evdev/uinput 系统级路径。

每个平台必须分别声明监听、注册、拦截、权限和恢复能力，不使用一个笼统的“支持”标记。

### 3. TypeScript/Node.js 与 Python 绑定

- TypeScript/Node.js 使用 Node-API。
- Python 绑定技术通过 ADR 决定。
- 两个绑定共享同一内核、事件模型、规则语义、能力和错误码。
- 语言层只做类型转换、生命周期、异步通知和语言习惯适配。
- 不把语言运行时放进原生输入决策路径。

### 4. 快捷键与动作触发

快捷键绑定和动作触发构建在输入内核之上，覆盖单键、组合、修饰键、鼠标按钮、长按、重复和冲突规则。它们不能在各语言绑定中分别实现成不同语义。

### 5. 测试、文档和发布

- 可重放事件序列和确定性规则测试。
- 生命周期、权限、Hook 失效、休眠、锁屏和热插拔测试。
- evdev、事件解码和规则输入的模糊测试。
- Node.js、Electron 和 Python 安装及集成示例。
- 平台能力矩阵、权限说明、API 文档和故障排查文档。
- 可审计的构建、预编译产物、校验和、SBOM 和发布说明。

## 明确不做什么

- 不做 GUI 配置器、托盘应用、宏录制器、RPA、游戏脚本或桌面自动化产品。
- 不把现有输入库或包装层作为 KeyMouse 内核。
- 不承诺覆盖锁屏、安全桌面、Secure Input、受保护进程或所有特权窗口。
- 不把系统快捷键注册等同于完整监听或任意事件拦截。
- 不在没有目标平台实测证据时宣称支持该平台。
- 不默认记录、持久化或上传键值、鼠标轨迹、窗口标题或应用内容。

## 开源怎么做

KeyMouse 采用普通库项目的轻量开源模式，不围绕商业版本或社区运营设计复杂流程。

- 完整源代码使用 `MIT OR Apache-2.0`，贡献采用同一许可证。
- 每个非合并提交要求 DCO sign-off，当前不要求 CLA。
- 功能、公共契约、native ABI、平台支持和安全策略通过 Issue、PR 或 ADR 公开讨论。
- CI 必须执行真实存在的检查；没有实现时不伪造构建、测试或平台支持。
- 公共能力声明必须有测试或平台证据支撑。
- 安全漏洞使用私密报告渠道；默认不采集用户输入数据。
- 发布使用 Semantic Versioning、CHANGELOG、CI 构建和可验证的发布产物。
- 英文是公共规范文档，中文保持同步维护。
- 当前由项目所有者维护；出现合适的长期贡献者后再增加维护者，不提前搭建复杂组织。

当前阶段以本文件作为唯一项目基线；后续实现、文档和自动化按阶段新增必要文件，不再保留历史调研与仓库脚手架。

## 阶段目标

| 阶段 | 目标 | 退出条件 |
| --- | --- | --- |
| Foundation | 固定公共契约和实现边界 | 事件模型、能力与错误语义、native 边界 ADR、威胁模型、重放测试骨架 |
| Vertical Slice | 打通原生内核到语言接口 | 模拟后端 + 一个真实后端；同步 `Pass` / `Consume`；一个语言绑定端到端验证 |
| Public Alpha | 让外部开发者安装和评估 | 两个语言绑定、一个稳定平台、可安装包、权限文档、能力矩阵和已知限制 |
| Cross-platform Beta | 证明架构可跨平台 | 四个目标环境按能力矩阵验证；第二平台在 API 冻结前完成；平台回归与预编译矩阵 |
| v1.0 | 形成可长期使用的库 | 稳定语义与 ABI 政策、支持范围、可验证发布、至少两名维护者、真实外部使用证据 |

阶段是质量门槛，不是发布日期。达不到门槛时继续补证据，不靠宣传绕过。

## 成功标准

- 用户无需理解四套平台 API 即可安装和集成 KeyMouse。
- TypeScript/Node.js 与 Python 对同一规则和事件表现一致。
- 声明支持的平台能力可以复现，失败、权限不足和降级状态清晰可见。
- 原生输入线程不会因语言运行时或业务回调阻塞。
- 默认不采集、不持久化、不上传用户输入内容。
- 文档、测试、示例和发布产物与当前版本一致。
- 至少存在独立应用或团队的真实使用证据，并能在不依赖维护者口头帮助的情况下升级。

不以 Star、下载量或提交数作为成功的主要证明。

## 尚未决定

- 最终项目名、npm/PyPI 名称、域名和品牌。
- native 边界采用稳定 C ABI、C++ API 或两者组合。
- Python 绑定技术。
- 首个真实平台后端及平台实现顺序。
- 版本支持窗口、首个正式发布身份和专用私密联系渠道。

这些事项在进入对应阶段前通过 ADR、Issue 或治理记录确定。
